# Challenges and Lessons Learned

Building this project was not only about training a classifier. The harder part was making the whole matching process reliable enough to run on large, messy business data.

## 1. The data was too large for naive matching

The first obvious approach would have been to compare every Source 1 business with every business in Sources 2 and 3. That creates a Cartesian product with far too many pairs to hold or process comfortably.

The solution was candidate generation, also called blocking. Instead of comparing everything, the pipeline creates a smaller set of plausible pairs using three rules:

- exact normalized name and address
- the first normalized business-name token
- country, a four-character name prefix, and the first address token

The candidate sets are then combined and deduplicated. This made the problem manageable, but it also introduced an important tradeoff: a true match missed during blocking cannot be recovered by the model later.

## 2. Real business data is inconsistent

The same business can appear with different punctuation, casing, abbreviations, or address formatting. Exact comparison alone therefore missed useful matches.

We added normalization for names and addresses before blocking and feature generation. For approximate comparison, the model uses token Jaccard similarity and character-bigram overlap for both names and addresses, along with a country-match feature.

These features are intentionally simple and interpretable. They are fast enough to use on many candidate pairs and make it easier to understand why a pair received a high or low score.

## 3. The model needed difficult negative examples

Randomly selected non-matches would have been too easy for the classifier. The more useful negative examples are the pairs that pass a blocking rule but are still incorrect.

The training set therefore consists of candidate pairs generated by the same blocking process used during inference. Ground-truth pairs become positives; the remaining candidates become hard negatives. This gives the Random Forest examples that look similar but should not be merged.

## 4. Accuracy was not the whole story

A matching system can have high accuracy simply because most pairs are non-matches. That number alone does not describe whether the system is creating bad business links.

The challenge emphasizes macro-averaged F0.5, which gives more importance to precision than recall. We hold out 20% of Source 1 entities, test 81 probability thresholds, and select the threshold with the best validation F0.5.

The pipeline also prints accuracy, precision, recall, and F1. These are reported as validation metrics, not as public test accuracy, because the test data has no labels available for comparison.

## 5. Performance work exposed hidden costs

The first feature implementation relied too heavily on row-wise string calculations. That became expensive as the candidate count grew. We replaced the slowest comparisons with lightweight bigram and token-overlap calculations, skipped repeated work for exact matches, and processed non-exact comparisons in chunks.

The benchmark itself also needed debugging. It initially reloaded and normalized the full training tables even when measuring only a small sample. That made the benchmark measure data preparation overhead instead of the sampled feature calculation. We changed it to reuse the sampled data, so the benchmark now reflects the operation it claims to measure.

The current recorded 200-row sample produced 47 candidate pairs:

- candidate generation: 0.25 seconds
- feature generation: 0.04 seconds

These are sample measurements, not a claim about full-dataset runtime.

## 6. Evaluation and output had edge cases

Ground-truth match IDs appeared with both spaces and commas as separators. The evaluation code now handles both formats. The output stage also preserves Source 1 entities with no accepted match as empty predictions, rather than silently dropping them.

This matters because a correct no-match decision is part of the task, not an exception to it.

## 7. Repository cleanup became part of the engineering work

The local data and generated TSV outputs were very large. They made the Git history too heavy for a normal push, even after the files were deleted from the working directory.

We added ignore rules, removed generated artifacts from tracked history, kept lightweight benchmark summaries, and documented how to reproduce the outputs locally. The GitHub repository now shows the code and decisions without publishing the challenge data.

## 8. The final interface came last

The Streamlit interface was added only after the pipeline, tests, and benchmark were working. It calls the existing pipeline rather than implementing a second matching flow. This keeps the dashboard useful for demonstration while preserving one source of truth for the model behavior.

The project currently has four passing regression tests covering normalization, blocking, and evaluation behavior.

## What I would improve next

The next improvements would be broader validation across multiple random splits, a more systematic comparison of blocking recall versus candidate volume, and a benchmark that records peak memory as well as runtime. Those measurements would give a stronger picture of how the pipeline behaves at full challenge scale.
